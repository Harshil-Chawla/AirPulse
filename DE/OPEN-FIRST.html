After moving DE to the repository root, run the same command from server using `../DE/run-queries.mjs` instead of `DE/run-queries.mjs`.

01-database-choice.md

# Database choice and architecture

AirPulse stores structured monitoring data: a station's identity, type, city and base coordinates, and repeated observations containing pollutant concentrations, AQI, location, source and timestamps. PostgreSQL fits this model because readings reference a stable station and the application needs temporal queries, joins and grouped statistics.

Foreign keys enforce station references, transactions support consistent writes, and indexes support recent history retrieval. SQL also supports independent analysis outside the ORM. MongoDB could store these records, but an unbounded history embedded in a station document would be a poor fit; relational station/readings tables are straightforward here. This is a project-specific choice, not a claim that PostgreSQL is universally superior.

Architecture: React/Vite browser → HTTPS Express API on Vercel → Prisma Client with PrismaPg adapter → Neon PostgreSQL. Local development uses a local PostgreSQL instance and the Vite API proxy. The production client uses VITE_API_URL; DATABASE_URL is a backend secret. DATABASE_URL_UNPOOLED is preferred by Prisma CLI for hosted migrations when supplied.

Prisma migrations create the database structure. The seed script creates three sample stations and their initial observations. It checks station names before creating samples, but name is not a database unique key, so concurrent seed runs are not guaranteed duplicate-free.

The mobile/drone simulator appends a measurement row. Measurements are simulated; the project does not currently ingest real sensor telemetry. Backend fusion/forecasting/source-attribution libraries are prototypes and are not exposed by application routes.

02-data-model.md

# Data model

Station has id (integer PK), name and city (text), type (StationType enum), latitude/longitude (double precision base coordinates), createdAt and updatedAt (timestamps).

Reading has id (integer PK), stationId (integer FK), nullable pm25, pm10, no2, so2, co and o3 (double precision), nullable aqi (integer), non-null latitude/longitude (observation coordinates), source (DataSource enum), recordedAt and createdAt (timestamps).

StationType = FIXED, MOBILE, DRONE. DataSource = CPCB, OPENAQ, OPEN_METEO, SIMULATED. Enum options do not establish that external providers are integrated.

One Station has zero or many Readings. Every Reading belongs to exactly one Station. stationId is NOT unique: multiple readings per station are expected. There is no required one-to-one or many-to-many relationship in this scope.

The FK references Station.id with ON DELETE CASCADE and ON UPDATE CASCADE in the SQL migration. Deleting a station deletes its historical readings, so deletion is demonstrated only on an isolated fixture.

Station coordinates describe the station's base; Reading coordinates describe an observation location. Neither stationId nor recordedAt alone identifies a reading. The current schema does not enforce uniqueness on their combination, station names or observation source/timestamp pairs.

PM2.5, PM10, NO2, SO2 and O3 are displayed in µg/m³; CO is displayed in mg/m³. AQI is a unitless index. Units are a project convention, not separate database metadata or CHECK constraints.

See diagrams/er-diagram.svg for a directly viewable diagram and er-diagram.mmd for editable Mermaid source. schema/schema.prisma and schema/migration.sql are the authoritative implemented definitions.

03-normalization.md

# Normalization through 3NF

## Assumptions and functional dependencies

Station.id → name, type, city, stationLatitude, stationLongitude, createdAt, updatedAt.
Reading.id → stationId, pollutant concentrations, aqi, readingLatitude, readingLongitude, source, recordedAt, createdAt.

Each station ID identifies one station. Names need not be unique. A timestamp and station pair is not a declared candidate key. Station and reading coordinates represent different facts. Reported AQI is treated as an independently supplied observation, not as a value functionally determined by the instantaneous pollutant columns: the project does not store all averaging windows and calculation metadata required to assert that dependency.

## Before normalization

A conceptual combined row could contain ReadingId, StationId, StationName, StationType, City, BaseLatitude, BaseLongitude, Pollutants, ObservationLocation and RecordedAt. Repeating station descriptors for every observation causes redundant storage.

Update anomaly: changing a station name would require changing many observations. Insertion anomaly: if station details existed only in observation rows, a station with no readings could not be represented cleanly. Deletion anomaly: deleting its last observation could remove station identity.

## First normal form

Represent observations as individual rows, not lists of historical measurements in a station cell. Give each row a key. Store each pollutant concentration and coordinate as an atomic column. These requirements address repeating groups; simply adding a surrogate key alone would not establish 1NF.

## Second normal form

Under the declared single-column ID candidate keys there can be no partial dependency on part of a composite key. The flattened observation design can therefore satisfy 2NF while still containing station redundancy. Do not incorrectly claim its decomposition is needed to remove a partial dependency on the surrogate ID.

## Third normal form

In the flattened design, ReadingId → StationId → StationName/Type/City/BaseCoordinates is a transitive dependency. Decompose station descriptors into Station, retaining stationId as the reference in Reading. The resulting tables have non-key facts dependent on their respective IDs, without a further non-key determinant under the stated assumptions.

The split is lossless for valid observations because stationId references a unique Station primary key. The FK prevents dangling references. Station descriptors can now be updated once, and stations can exist without readings.

A separate City entity or Pollutant entity is not automatically necessary for this scope. City has no additional dependent attributes here; a long-format pollutant table may become useful when variable sensor types or per-measurement unit metadata are introduced.

The authoritative final normalized structure is in schema/. Normalization does not by itself guarantee measurement validity, prevent duplicate telemetry, or make measurements representative of an area.

schema/migration.sql

-- CreateEnum
CREATE TYPE "StationType" AS ENUM ('FIXED', 'MOBILE', 'DRONE');

-- CreateEnum
CREATE TYPE "DataSource" AS ENUM ('CPCB', 'OPENAQ', 'OPEN_METEO', 'SIMULATED');

-- CreateTable
CREATE TABLE "Station" (
    "id" SERIAL NOT NULL,
    "name" TEXT NOT NULL,
    "type" "StationType" NOT NULL,
    "city" TEXT NOT NULL,
    "latitude" DOUBLE PRECISION NOT NULL,
    "longitude" DOUBLE PRECISION NOT NULL,
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    "updatedAt" TIMESTAMP(3) NOT NULL,

    CONSTRAINT "Station_pkey" PRIMARY KEY ("id")
);

-- CreateTable
CREATE TABLE "Reading" (
    "id" SERIAL NOT NULL,
    "stationId" INTEGER NOT NULL,
    "pm25" DOUBLE PRECISION,
    "pm10" DOUBLE PRECISION,
    "no2" DOUBLE PRECISION,
    "so2" DOUBLE PRECISION,
    "co" DOUBLE PRECISION,
    "o3" DOUBLE PRECISION,
    "aqi" INTEGER,
    "latitude" DOUBLE PRECISION NOT NULL,
    "longitude" DOUBLE PRECISION NOT NULL,
    "source" "DataSource" NOT NULL,
    "recordedAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT "Reading_pkey" PRIMARY KEY ("id")
);

-- CreateIndex
CREATE INDEX "Reading_stationId_recordedAt_idx" ON "Reading"("stationId", "recordedAt");

-- CreateIndex
CREATE INDEX "Reading_recordedAt_idx" ON "Reading"("recordedAt");

-- AddForeignKey
ALTER TABLE "Reading" ADD CONSTRAINT "Reading_stationId_fkey" FOREIGN KEY ("stationId") REFERENCES "Station"("id") ON DELETE CASCADE ON UPDATE CASCADE;

# Query explanations and expected results

Execute with run-queries.mjs, which installs the fixture, runs queries.sql inside the same transaction and rolls it back. Do not run queries.sql alone against the production public schema.

The following are EXPECTED results from the deterministic fixture, not execution receipts:

| Query | Purpose / SQL concept | Expected fixture result |
|---|---|---|
| Q01 | Select mobile stations in Delhi; WHERE | Station 2 |
| Q02 | Recent history; ORDER BY/LIMIT | Reading IDs 4, 3, 2 |
| Q03 | Attribute measurements to stations; INNER JOIN | Four observation rows |
| Q04 | Historical summaries; LEFT JOIN, COUNT, AVG, MAX, GROUP BY | Fixed: count 1/avg 165; mobile: count 2/avg 195/max 200; drone: count 1/avg 135 |
| Q05 | Repeated elevated readings; HAVING | Station 2, elevated_count 2 |
| Q06 | Compare latest reporting values; DISTINCT ON | Station AQIs 165, 200, 135 |
| Q07 | Find above-own-average observations; correlated subquery | Reading 4, AQI 200 |
| Q08 | Retrieve a measurement interval; inclusive time filters | Reading 4 |
| Q09 | Register a temporary monitoring asset; INSERT RETURNING | Station 900 |
| Q10 | Correct station identity; UPDATE RETURNING | Corrected name on station 900 |
| Q11 | Append an observation; INSERT with FK | Reading 900 references station 900 |
| Q12 | Retire test asset; DELETE plus cascade check | Station 900 deleted; zero remaining readings for 900 |

Fixed AQI thresholds here are selection criteria for a demonstration, not health advice. Grouped averages summarize stored history; they are not official regional AQIs. MAX in Q04 is the maximum historical observation, distinct from the dashboard's highest latest-station value. RecordedAt and id are both used for deterministic ordering where applicable.

Expected results are useful for explaining the query but do not replace the mandatory actual execution output in evidence/query-execution.txt.

queries.sql

-- Q01 — Delhi mobile stations
SELECT id,name,type,city FROM "Station" WHERE city='Delhi' AND type='MOBILE' ORDER BY id;

-- Q02 — Latest observation history
SELECT id,"stationId",aqi,"recordedAt" FROM "Reading" ORDER BY "recordedAt" DESC,id DESC LIMIT 3;

-- Q03 — Station and observation join
SELECT s.name,s.type,r.aqi FROM "Station" s JOIN "Reading" r ON r."stationId"=s.id ORDER BY r.id;

-- Q04 — Per-station summary including stations without observations
SELECT s.id,s.name,COUNT(r.id) AS reading_count,ROUND(AVG(r.aqi),1) AS average_aqi,MAX(r.aqi) AS highest_aqi FROM "Station" s LEFT JOIN "Reading" r ON r."stationId"=s.id GROUP BY s.id,s.name ORDER BY s.id;

-- Q05 — Repeated elevated observations
SELECT "stationId",COUNT(*) AS elevated_count FROM "Reading" WHERE aqi>100 GROUP BY "stationId" HAVING COUNT(*)>=2 ORDER BY "stationId";

-- Q06 — Latest reading from every reporting station
SELECT DISTINCT ON (s.id) s.id,s.name,r.aqi,r."recordedAt" FROM "Station" s JOIN "Reading" r ON r."stationId"=s.id ORDER BY s.id,r."recordedAt" DESC,r.id DESC;

-- Q07 — Above-station-average readings
SELECT r.id,r."stationId",r.aqi FROM "Reading" r WHERE r.aqi>(SELECT AVG(h.aqi) FROM "Reading" h WHERE h."stationId"=r."stationId") ORDER BY r.id;

-- Q08 — Measurement time range
SELECT id,"stationId",aqi FROM "Reading" WHERE "recordedAt">='2026-11-14 10:00:30' AND "recordedAt"<='2026-11-14 10:01:00' ORDER BY id;

-- Q09 — Register a station
INSERT INTO "Station" (id,name,type,city,latitude,longitude,"updatedAt") VALUES (900,'DE recording station','MOBILE','Delhi',28.61,77.21,CURRENT_TIMESTAMP) RETURNING id,name;

-- Q10 — Correct station metadata
UPDATE "Station" SET name='DE recording station corrected',"updatedAt"=CURRENT_TIMESTAMP WHERE id=900 RETURNING id,name;

-- Q11 — Record a measurement
INSERT INTO "Reading" (id,"stationId",aqi,latitude,longitude,source) VALUES (900,900,150,28.611,77.211,'SIMULATED') RETURNING id,"stationId",aqi;

-- Q12 — Retire the demonstration station and verify cascade
DELETE FROM "Station" WHERE id=900 RETURNING id,name;
SELECT COUNT(*) AS remaining_station_readings FROM "Reading" WHERE "stationId"=900;

# Backend integration and evidence

## Implemented operations

GET /api/stations → fetchStations → getAllStations → prisma.station.findMany with the latest Reading. Conceptually SELECT stations plus the most recent associated reading.

GET /api/stations/:id/readings → validated stationId/historyOptions → getStationReadings → prisma.reading.findMany WHERE stationId with optional date bounds, ordered by recordedAt descending and bounded by limit.

GET /api/stations/:id/stats → getStationAggregates → summary of bounded reading history. These statistics cover loaded rows, not necessarily every historical measurement.

POST /api/stations/:id/simulate-movement and /simulate-drone-movement → type validation → Prisma reading.create → SQL INSERT into Reading. ENABLE_SIMULATION must be true. Sample measurements and coordinates are simulated; nothing controls a physical station.

src/lib/prisma.js constructs PrismaClient with PrismaPg using DATABASE_URL. prisma.config.ts uses the direct connection when configured for CLI migrations. Source files are in server/src/{routes,controllers,services,lib}.

06-integrity-performance.md

# Integrity and performance

Implemented database safeguards: primary keys, NOT NULL for required identity/location/source/time fields, foreign key Station→Reading, enum types and cascade deletion. Nullable pollutant values distinguish unknown measurements from zero.

Application code validates station IDs, history limits and dates. normalizeReading rejects missing/blank/boolean coordinates and invalid numeric measurements, but this helper is not an exposed ingestion route. It must not be described as database-enforced validation. There are no database CHECK constraints for valid coordinate ranges, nonnegative pollution or 0–500 AQI. Direct SQL can bypass application validation.

Station names are not unique. Observation deduplication is not implemented; repeated timestamps can be stored. Sequence IDs establish identity but do not prove two rows represent different physical sensor samples. Future ingestion should use a provider/device observation key and an appropriate uniqueness policy.

The composite Reading(stationId, recordedAt) index supports station equality plus temporal filtering/sorting. Reading(recordedAt) supports cross-station time searches. Primary key indexes support identifier lookups. LIMIT bounds returned rows but does not itself bound retained history. Do not claim an index always makes a query faster; use EXPLAIN (ANALYZE, BUFFERS) on SELECT queries with representative data. A sequential scan can be preferable for this tiny seed dataset.

Larger deployments can use keyset pagination ordered by recordedAt and id, database-side aggregation, retention/partitioning policies, bounded caching and suitable pooling. Current station-existence cache is bounded at 1000 entries and has a 60-second TTL; it can briefly reflect stale metadata after external changes.

The normalization helper raises PM10 to PM2.5 when an inversion occurs. This is a demo sanitization policy, not scientifically validated calibration. Real ingestion should preserve raw data and attach quality flags rather than silently correcting observations without provenance.

Public simulation endpoints allow writes when enabled and have no user authentication or per-user authorization. Disable them unless an intentional public demonstration is required.
